오늘은 수강신청 데이터(analysis_lab 스키마, 신청 24건)를 SQL로 집계하고, 같은 데이터를 pandas로 다시 계산해서 두 결과를 비교하는 실습을 했다. 핵심 원칙은 한 줄이다.

그래프가 만들어졌다고 분석이 검증된 것은 아니다. 질문 → 기간 → 한 행의 의미 → 지표 정의 → SQL 기준값 → pandas 결과 → 교차 검증이 모두 일치해야 한다.

오늘의 한 줄 정리

  • SQL은 DB 안에서 기간·상태·JOIN을 확정하고 기준값을 만든다. pandas는 같은 VIEW로 피벗·분포·그래프·실험을 빠르게 해 본다.
  • 둘이 일치할 때만 "둘 다 맞다"고 말할 수 있고, 일치하지 않으면 기대값이 아니라 질문의 정의부터 본다.
  • 오류 없이 실행됐다는 것은 문법이 맞다는 뜻이지 결과가 맞다는 뜻이 아니다.

1. SQL보다 먼저 "질문 계약"을 쓴다

쿼리를 쓰기 전에 아래 항목을 문장으로 정한다.

항목 예시
업무 질문 상반기에 매월 수강신청이 몇 건이고, 기록된 금액 합계는?
분석 기간 [2026-01-01, 2026-07-01)
날짜 기준 enrolled_at(신청일) — 완료일·결제일이 아님
한 행의 의미 결과 1행 = 1개월
포함/제외 상태 취소도 "신청은 발생"했으므로 포함
검산 방법 6개월 건수 합 = 24, 금액 합 = 3,210,000

기간은 반개방 구간 [start, end)로

BETWEEN '2026-01-01' AND '2026-06-30'처럼 닫힌 구간을 쓰면 timestamp일 때 6월 30일 00:00 이후 값이 빠지고, 다음 기간을 이어 붙일 때 경계일이 두 번 들어갈 수 있다.

WHERE enrolled_at >= DATE '2026-01-01' AND enrolled_at < DATE '2026-07-01'

날짜든 시간이든 경계가 명확하고, 기간끼리 이어 붙여도 겹치거나 빠지는 행이 없다.

지표 이름이 곧 해석이다

recorded_amount는 "신청 시점에 행에 기록된 금액"이다. 이 스키마에는 결제 승인·환불 테이블이 없고, 취소된 신청(3건, 440,000)과 결제 여부를 알 수 없는 '신청' 상태도 포함되어 있다. 그래서 이 합계를 매출이라고 부르면 실제로 받지 않은 돈까지 매출로 보고하는 셈이 된다.

2. 집계 전에 데이터 품질부터, 그룹 합계는 전체와 비교

PK 중복, 고아 FK, 완료인데 completed_at이 없는 행, 완료일 < 신청일 같은 이상 건수를 먼저 0으로 확인한다.

  • 집계는 이상한 행도 오류 없이 그대로 더한다.
  • SQL은 "쓴 대로" 정확히 계산할 뿐, 원본이 맞는지는 판단하지 않는다. 잘못된 원본 → 정확한 SQL → 정확하게 잘못된 집계.

그룹 합계도 전체와 다시 비교한다. 상태별 건수(신청 4 + 수강중 5 + 완료 12 + 취소 3)의 합이 전체 24건과 같은지 확인한다. WHERE나 JOIN 때문에 일부 행이 빠지거나(NULL 상태, INNER JOIN 누락) 늘어났다면 합이 맞지 않는다. 합이 같아야 "모든 행이 정확히 한 그룹에 한 번씩 들어갔다"는 것이 확인된다.

3. date spine: 0건인 달도 행으로 남기기

실제 데이터만 GROUP BY하면 신청이 0건인 달은 결과 행 자체가 생기지 않는다. 6개월 분석인데 5행만 나와도 SQL은 오류를 내지 않는다.

-- (개념 이해용 예시 쿼리) 달력을 먼저 만들고, 집계를 LEFT JOIN
WITH months AS (
    SELECT generate_series(DATE '2026-01-01', DATE '2026-06-01', INTERVAL '1 month')::date AS month
)
SELECT m.month, COALESCE(COUNT(e.enrollment_id), 0) AS enrollment_count
FROM months m
LEFT JOIN enrollments e ON date_trunc('month', e.enrolled_at)::date = m.month
GROUP BY m.month
ORDER BY m.month;
  • "그 달 0건"도 중요한 관찰이다. 행이 사라지면 0건인지 데이터를 못 가져온 것인지 구분할 수 없다.
  • LAG는 "직전 행"이지 "직전 달"이 아니다. 4월이 빠지면 5월의 LAG가 3월 값이 되어, 두 달 차이를 "전월 대비 증감"으로 잘못 해석한다. date spine 위에서 계산해야 진짜 전월 비교다.

4. 분석 VIEW의 행 단위가 깨지면 모든 지표가 틀린다

VIEW에서 1:N 테이블을 잘못 JOIN해서 신청 1건이 2행이 되면 pandas의 count와 sum이 모두 부풀려진다. pandas는 그 행이 중복인지 모르고, SQL 기준값과 비교하기 전까지는 그래프도 그럴듯해 보인다. 그래서 "한 행 = enrollment_id 1개"를 행 수와 고유 ID 수 비교로 확인한다.

5. 분석용 연결은 읽기 전용으로

default_transaction_read_only = on

분석 코드는 데이터를 읽기만 해야 한다. 실수로 UPDATE/DELETE가 섞이거나 AI가 만든 코드가 데이터를 바꾸면 비교의 의미가 없어진다. 읽기 전용으로 연결하면 쓰기 시도 자체를 DB가 거부하므로 "분석이 원본을 바꾸지 않았다"는 것을 코드 리뷰가 아니라 DB가 보장한다.

같은 REPEATABLE READ 읽기 전용 스냅샷에서 SQL과 pandas를 둘 다 실행하면 정확히 같은 시점의 데이터를 본다. 결과가 다르다면 데이터 변경이 아니라 계산 로직의 차이라고 확신할 수 있다.

6. PostgreSQL 18: NOT NULL도 pg_constraint에 기록된다

최종 검증 쿼리가 "제약조건은 20개여야 하는데 40개"라며 실패했다. 기대값을 40으로 바꾸지 않고 종류별로 나눠 봤다.

SELECT contype, count(*)
FROM pg_constraint
WHERE connamespace = 'analysis_lab'::regnamespace
GROUP BY 1;
contype 의미 개수
c CHECK 12
f FOREIGN KEY 3
p PRIMARY KEY 4
u UNIQUE 1
n NOT NULL 20

PK·FK·UNIQUE·CHECK는 정확히 20개였고, 늘어난 20개는 전부 n(NOT NULL)이었다. PostgreSQL 18부터 NOT NULL도 pg_constraint에 행으로 기록되기 때문이다. 데이터나 구조의 문제가 아니라 PG17 이하 기준으로 쓴 검증 쿼리의 버전 차이였다. 원본 파일은 건드리지 않고 복사본에서만 AND contype <> 'n'을 추가했다.

실패했을 때 기대값을 현재 결과에 맞춰 고치면 안 된다. 기대값은 "맞는 상태"의 정의다. 40으로 바꾸면 진짜로 제약조건이 중복 생성된 경우에도 통과시킨다.

7. pandas에서 문제를 숨기는 세 가지

코드 위험
errors='coerce' 잘못된 날짜·숫자를 오류 없이 NaN으로 바꿈
dropna() 그 NaN 행을 경고 없이 삭제 (24행 → 22행)
drop_duplicates() JOIN 중복이라는 진짜 원인을 숨기고 숫자만 맞춰 보이게 함

이 데이터의 completion_days는 미완료 12건이 정상적으로 NaN이라, 전체에 dropna()를 하면 절반이 사라진다. 완료 기간을 계산할 때만 "완료 상태만 필터"처럼 업무 기준이 분명한 조건으로 대신한다. 삭제하기 전에 "어떤 행이 왜 이상한가"를 먼저 확인한다.

8. 통제된 불일치 실험

조건을 하나만 바꿔서 비교가 불일치를 잡아내는지 확인했다.

변경한 조건 결과 변화 원인
취소 상태를 제외 24행 → 21행, 금액 3,210,000 → 2,770,000 질문 정의가 달라짐 (취소도 신청 발생으로 셈)
분석 시작일을 2월 1일로 1월 3건이 통째로 빠지고 완료·취소 건수까지 달라짐 기간 정의 불일치가 모든 지표로 번짐

숫자가 다를 때 "어느 쪽 숫자를 고칠까"가 아니라 "두 쪽의 질문 정의(기간·상태·행 단위)가 같은가"를 먼저 본다. 행 수 → 금액 → 그룹별 순으로 비교하면 원인을 빨리 좁힐 수 있다.

9. SQL과 pandas 결과가 다를 때 확인 순서

  1. 같은 DB·같은 VIEW를 보고 있는가
  2. 같은 시점의 데이터인가 (스냅샷, CSV라면 SHA-256·생성 시각)
  3. 분석 기간과 날짜 기준이 같은가 ([start, end), enrolled_at 기준)
  4. 한 행의 단위가 같은가 (행 수와 고유 ID 수)
  5. 취소·NULL 처리 기준이 같은가
  6. 자료형 변환 중 행이나 값이 사라지지 않았는가 (coerce/dropna)

CSV로 전달할 때는 manifest(출처·기간·생성 시각)와 SHA-256이 있어야 "이 파일이 그때 그 VIEW 그대로"임을 다시 확인하고 재현할 수 있다.

10. 관찰·해석·한계를 분리해서 쓴다

  • 관찰(검증된 사실): 완료 12건의 평균 완료 기간은 25일이다.
  • 해석(내 판단): 학생들은 평균 25일이면 수료한다 → 이건 잘못된 일반화다.
  • 한계: 평균은 '완료' 12건만으로 계산했다. 수강중 5건과 신청 4건은 아직 끝나지 않았고 나중에 더 오래 걸려 완료될 수 있다(관찰이 잘린 데이터). 합성 데이터 24건, 6개월뿐이다.

섞어 쓰면 읽는 사람이 추측을 사실처럼 받아들인다. 분리해 두면 어디까지가 검증된 숫자이고 어디부터가 판단인지 분명해진다.

11. AI를 분석 리뷰어로 쓰기

AI에게 "그래프 디자인보다 먼저 질문·기간·한 행의 의미·JOIN 중복·NULL 처리·자료형 변환을 확인해 달라"고 요청하고, 제안을 실제 결과로 검토했다.

AI 제안 판단 이유
40개는 PG18 NOT NULL 때문이니 contype <> 'n'으로 세자 수정 후 수용 contype별 집계로 원인을 확인했고 기대값은 그대로 둠
기대값을 40으로 바꾸면 통과한다 거절 진짜 중복 제약도 통과시킴
dropna()로 정리하자 거절 정상 결측 12건이 사라져 24행이 12행이 됨
취소 건을 금액에서 빼자 보류 현재 질문은 "신청 시점 기록 금액"이라 포함이 맞음

AI 코드가 오류 없이 돌아가고 그래프가 깔끔해도, 기간이나 상태 필터 하나만 달라도 숫자는 틀린다. 그래프는 틀린 숫자도 똑같이 예쁘게 그리므로 SQL 기준값과 일치하는지를 먼저 확인한다.

마무리

SQL은 DB 안에서 기간·상태·JOIN을 확정하고 기준값을 만드는 역할, pandas는 같은 VIEW로 피벗·분포·그래프·실험을 빠르게 해 보는 역할이다. 둘이 일치할 때만 "둘 다 맞다"고 말할 수 있고, 일치하지 않으면 기대값이 아니라 질문의 정의부터 본다.
