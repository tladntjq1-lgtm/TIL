오늘 데일리 퀘스트는 서버가 요청을 처리하는 방식(WSGI와 ASGI), 로그 레벨, 로깅 설정을 logger.py로 분리하는 이유, 그리고 --reload 옵션을 다뤘다. 풀고 나서 틀린 문제가 있어서, 어떤 점을 헷갈렸는지 오답노트까지 함께 정리해 둔다.

오늘의 한 줄 정리

  • WSGI는 요청마다 스레드를 1:1로 할당하고, ASGI는 단일 스레드의 이벤트 루프가 코루틴을 번갈아 실행한다.
  • 로그는 설정한 레벨 이상만 출력된다. DB 커넥션 풀 고갈은 WARNING이 아니라 CRITICAL 이다.
  • 로깅 설정은 엔드포인트 코드에 인프라 설정이 섞이지 않게 logger.py로 분리한다.
  • --reload는 개발 편의용이고, 운영에서는 제외한다.

1. WSGI vs ASGI: 요청을 처리하는 방식이 다르다

WSGI ASGI
처리 방식 요청마다 OS 스레드를 1:1로 할당해서 순차 처리 단일 스레드가 이벤트 루프로 여러 코루틴을 번갈아 실행
한 줄 요약 요청 하나에 일꾼(스레드) 하나 일꾼 한 명이 기다리는 동안 다른 일을 처리
I/O 대기 중 스레드가 블로킹 상태로 멈춰 있음 대기하는 코루틴은 양보하고 다른 코루틴이 실행됨

ASGI의 본질은 협력적 멀티태스킹(cooperative multitasking) 이다. 코루틴이 스스로 await에서 실행권을 넘겨주고, 이벤트 루프가 그 사이에 다른 코루틴을 실행한다.

I/O 대기와 블로킹 상태

WSGI에서 DB 쿼리나 외부 API 요청처럼 I/O 대기가 생기면, 그 요청을 맡은 스레드는 응답이 올 때까지 블로킹 상태로 기다린다. 동시 요청이 많아지면 스레드 풀의 스레드가 모두 대기 중이 되어 스레드 풀 자원이 고갈될 수 있다.

WSGI : 요청A → [스레드1: DB 응답 대기 (블로킹)]
       요청B → [스레드2: 외부 API 응답 대기 (블로킹)]   ← 스레드가 다 차면 새 요청이 대기
ASGI : 요청A, 요청B → [스레드 1개 + 이벤트 루프] A가 기다리는 동안 B를 실행

FastAPI는 ASGI 서버(Uvicorn) 위에서 동작한다. 이전 글에서 쓴 uvicorn main:app의 Uvicorn이 ASGI 서버다.

2. 로그 레벨

로그는 중요도에 따라 레벨을 나눠서 기록한다. 낮은 레벨일수록 자세하고, 높은 레벨일수록 심각하다.

레벨 값 용도
DEBUG 10 개발 중 상세 추적. 실행된 SQL 쿼리문 출력
INFO 20 정상적인 동작 기록 (서버 시작, 요청 처리 완료)
WARNING 30 당장은 문제없지만 주의가 필요한 상황
ERROR 40 특정 기능이 실패한 오류
CRITICAL 50 시스템 전체가 마비될 수 있는 치명적 상황. DB 커넥션 풀 고갈

설정한 레벨 이상의 로그만 출력된다. 예를 들어 INFO로 설정하면 DEBUG는 출력되지 않는다.

오답 포인트: "DB 커넥션 풀 고갈"은 WARNING이 아니라 CRITICAL 이다. 새 요청이 DB에 접근할 수 없게 되어 시스템 전체가 멈출 수 있기 때문이다.

3. 로깅 설정을 logger.py로 분리하는 이유

아래 코드는 개념 이해용 예시다.

# logger.py (개념 이해용 예시)
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(name)s - %(message)s",
)
logger = logging.getLogger("app")

# main.py
from fastapi import FastAPI
from logger import logger

app = FastAPI()

@app.get("/members")
def get_members():
    logger.info("회원 목록 조회")
    return []

분리하는 이유

  • API 엔드포인트 코드에 시스템 인프라 설정이 섞이지 않게 한다.
  • 설정을 한 곳에서 관리하고 여러 모듈이 같은 로거를 가져다 쓴다.

분리의 목적이 아닌 것: logging 모듈은 순수한 기록용 표준 라이브러리다. 워커 프로세스 관리나 서버의 물리적 처리 속도 향상과는 무관하다.

4. --reload: 코드 변경을 감지해 서버 자동 재시작

python -m uvicorn main:app --reload --port 8010

--reload를 쓰면 파일 워처가 소스 코드 변경을 감지해서 서버를 자동으로 재시작한다(핫 리로드). 코드를 저장하고 Swagger를 새로고침만 하면 된다.

운영(프로덕션)에서는 제외한다. 파일을 계속 감시하는 것 자체가 부담이라 성능이 떨어진다. 개발 편의용 옵션이다.

오답노트 (2026-11-02)

  • 1번: ASGI의 특징을 WSGI의 특징으로 골랐다. "요청마다 스레드를 1:1로 할당해 순차 처리"는 WSGI다. ASGI는 "단일 스레드 + 이벤트 루프 + 코루틴 번갈아 실행"이다. 키워드로 외우면 스레드 1:1 = WSGI, 이벤트 루프 = ASGI.
  • 3번, 4번: "올바르지 않은 것", "타당하지 않은 것"을 묻는 부정 문제를 거꾸로 읽었다.
  • 3번에서 고른 DEBUG - SQL 쿼리문 출력은 올바른 연결이었다. 틀린 연결은 WARNING - DB 커넥션 풀 고갈(정답은 CRITICAL)이었다.
  • 4번에서 고른 "엔드포인트 영역에 인프라 설정이 섞이지 않게"는 타당한 이유였다. 타당하지 않은 것은 "워커 프로세스 관리나 처리 속도 향상" 같은 설명이었다.
  • 선지를 읽을 때마다 "이게 맞는 설명인가?"를 먼저 판단한 뒤, 문제가 요구하는 쪽(맞는 것 또는 틀린 것)으로 거르는 습관이 필요하다.
