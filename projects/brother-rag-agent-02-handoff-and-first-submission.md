## 2일차 (11/21): 인수인계 준비

**한 일**
- 첫 공식 제출일(11/23)에 자리를 비우게 되어, **혼자 따라 할 수 있는 인수인계 문서** `docs/handoff_C_to_A.md`를 작성했다.
- **서버 실행 → 터널 → 포털 제출 → DEV 평가**를 **9단계 체크리스트**로 정리하고, 단계마다 **성공 기준**을 넣었다.

**배운 것**
- 인수인계 문서는 "무엇을 하라"보다 **"이렇게 보이면 성공"**이 있어야 혼자 따라 할 수 있다.
- 모든 절차를 **직접 실행해서 실제 응답을 문서에 붙여 두면** 화면과 비교하기 쉽다.

## 3일차 (11/22): 응답 규격 검증

**한 일**
- 응답의 **`usage`**(공식 모델명, 입력·출력·총 토큰) 규격을 **정상·거부·오류 응답 모두**에서 검증했다. (#43)

**배운 것**
- 토큰 사용량은 **생성 호출만이 아니라 실패한 호출까지 이미 쓴 만큼** 기록해야 한다.
- **임베딩 호출은 따로 구분**한다.

| 응답 종류 | `usage` 검증 |
|---|---|
| 정상 응답 | 검증함 |
| 거부 응답 | 검증함 |
| 오류 응답 | 검증함 (실패한 호출도 이미 쓴 만큼) |

## 4일차 (11/23): 첫 공식 제출 (자리를 비운 날)

**한 일**
- 자리를 비운 날이다. **팀이 인수인계 문서로 서버와 터널을 띄워** 첫 공식 제출을 진행했다.

**배운 것**
- **미리 써 둔 체크리스트 덕분에** 담당자가 없어도 제출이 돌아갔다.
- 반대로 **"PC + 터널" 구조는 PC가 꺼지면 평가 전체가 실패**한다는 위험이 보였다. 이것이 11/24 **클라우드 배포**로 이어졌다.

## 정리

- 인수인계 문서의 핵심은 **성공 기준과 실제 응답 예시**다.
- 응답 규격은 **정상·거부·오류 모두**에서 검증한다.
- 로컬 PC에 의존하는 구조는 **단일 실패 지점**이 된다.
