오늘은 여러 테이블을 합치는 JOIN과 UNION의 차이를 정리하고, GROUP BY와 HAVING, LIKE를 익혔다. 그리고 PostgreSQL과 DBeaver로 스키마와 테이블을 직접 만들고 CRUD를 실습했다. 틀리기 쉬운 포인트는 따로 표시해 두었다.

오늘의 한 줄 정리

  • UNION은 세로(행) 방향으로 쌓고, JOIN은 가로(열) 방향으로 연결한다. 열 수와 타입을 맞춰야 하는 건 UNION뿐이다.
  • LEFT JOIN에서 짝이 없는 쪽은 0이 아니라 NULL 로 채워진다.
  • 집계 결과에 조건을 걸 때는 WHERE가 아니라 HAVING 을 쓴다.

1. UNION vs JOIN, 방향이 다르다

  • UNION: 같은 구조의 SELECT 결과를 세로(행) 방향으로 쌓는다. 열 개수와 데이터 타입이 동일해야 한다. ON 절이 필요 없다.
  • JOIN: 공통 키를 기준으로 서로 다른 테이블을 가로(열) 방향으로 연결한다. ON 절이 필요하다.

열 수와 타입이 일치해야 한다는 조건은 UNION에만 해당되고, JOIN에는 해당되지 않는다.

2. INNER JOIN, 교집합만

SELECT *
FROM customers
INNER JOIN orders ON customers.id = orders.customer_id;

두 테이블 모두에 일치하는 행만 반환한다. 어느 한쪽에만 존재하는 행은 결과에서 제외된다. 가장 기본적이고 많이 쓰이는 JOIN이다.

3. LEFT JOIN, 왼쪽 테이블은 전부 유지

SELECT *
FROM customers
LEFT JOIN orders ON customers.id = orders.customer_id;

왼쪽 테이블(customers)의 모든 행을 포함하며, 오른쪽 테이블에 일치하는 행이 없으면 그 열은 NULL로 채워진다. 0이 아니라 NULL이라는 점이 자주 틀리는 포인트다. 즉 주문이 없는 고객도 결과에 포함되고, orders 관련 값만 NULL이 된다.

개념 이해용 예시

아래 데이터는 원본 노트에 없는, 이해를 돕기 위해 내가 만든 간단한 예시다. 고객 3명 중 한 명은 주문이 없다고 가정한다.

customers.id customers.name orders.customer_id
1 홍길동 1 (주문 있음)
2 김영희 2 (주문 있음)
3 이철수 (주문 없음)
  • INNER JOIN 결과: 홍길동, 김영희만 나온다. 이철수는 제외된다.
  • LEFT JOIN 결과: 세 명 모두 나온다. 이철수의 orders 쪽 열은 NULL이다.

4. GROUP BY와 HAVING

  • WHERE절은 GROUP BY 전에 실행되므로, 집계 함수의 결과를 조건으로 사용할 수 없다. 그렇게 작성하면 에러가 난다.
  • 집계 결과에 조건을 걸려면 반드시 HAVING을 사용해야 한다.
SELECT category, COUNT(*) AS product_count
FROM products
GROUP BY category
HAVING COUNT(*) > 10;   -- 집계 결과(개수)에 대한 조건이므로 WHERE가 아니라 HAVING

5. LIKE, 문자열 포함 검색

SELECT * FROM products
WHERE name LIKE '%Trek%';

LIKE는 %를 활용해 특정 문자열을 포함하는 패턴을 조회할 때 사용한다. IN은 정확히 일치하는 값만 찾는 반면, LIKE는 앞뒤에 어떤 값이 오더라도 지정한 문자열이 포함되면 조회된다.

6. PostgreSQL과 DBeaver

  • PostgreSQL: 데이터를 실제로 저장하고 관리하는 데이터베이스 서버(DBMS)다. 데이터를 보관하는 창고에 비유할 수 있다.
  • DBeaver: 데이터베이스를 다루는 GUI 툴이다. "데이터베이스에서 VS Code 같은 느낌"의 도구다.

7. 스키마와 테이블 만들기

-- 1. 스키마 생성
CREATE SCHEMA practice;

-- 2. 테이블 생성
CREATE TABLE practice.members (
    member_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    age INTEGER,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
  • GENERATED ALWAYS AS IDENTITY: PK를 자동 증가시킨다.
  • UNIQUE NOT NULL: 이메일처럼 중복 없이 반드시 값이 있어야 하는 컬럼에 사용한다.
  • DEFAULT CURRENT_TIMESTAMP: 값을 넣지 않으면 생성 시각이 자동으로 채워진다.

8. CRUD 실습

-- Create
INSERT INTO practice.members (name, email, age)
VALUES
    ('홍길동', 'hong@example.com', 25),
    ('김영희', 'younghee@example.com', 31),
    ('이철수', 'chulsoo@example.com', 28),
    ('박민지', 'minji@example.com', 23);

-- Read (전체 조회)
SELECT * FROM practice.members;

-- Read (조건 조회)
SELECT * FROM practice.members WHERE age >= 30;

-- Update
UPDATE practice.members
SET age = 26
WHERE email = 'hong@example.com';

-- Delete
DELETE FROM practice.members
WHERE email = 'minji@example.com';

-- 최종 확인
SELECT * FROM practice.members ORDER BY member_id;

UPDATE와 DELETE는 WHERE 조건으로 대상 행을 지정했다. 실습에 쓴 이메일은 모두 예시용 값이다.

9. Django에서 특정 스키마를 우선 검색하게 하기

Django settings.py의 DATABASES["default"]["OPTIONS"]에 search_path를 지정하면, 여러 스키마 중 원하는 스키마를 먼저 검색하도록 만들 수 있다.

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": "...",
        "USER": "...",
        "PASSWORD": "...",   # 실제 값은 .env로 관리하고 절대 커밋하지 않는다
        "HOST": "...",
        "PORT": "...",
        "OPTIONS": {
            "options": "-c search_path=practice",
        },
    }
}

접속 정보는 위처럼 ...로 비워 두었다. 실제 값은 .env로 관리하고 커밋하지 않는다.

10. Git 추적 관련 메모

git rm --cached <파일> 명령은 로컬 파일은 그대로 두고 Git의 추적만 해제한다. 비밀번호가 담긴 설정 파일을 실수로 커밋했을 때 활용할 수 있다. 다만 이미 푸시된 이력에는 남아 있으니 .gitignore를 먼저 등록하는 것이 우선이다.

복습: 헷갈리기 쉬운 포인트

  • UNION은 세로, JOIN은 가로다. 열 수와 타입 일치 조건은 UNION에만 해당한다.
  • LEFT JOIN에서 짝이 없는 값은 0이 아니라 NULL이다.
  • 집계 결과(COUNT(*) 등)에 조건을 걸 때는 WHERE가 아니라 HAVING이다.
  • LIKE '%문자열%'은 포함 검색이고, IN은 정확히 일치하는 값만 찾는다.
