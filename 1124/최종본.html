프로젝트 5일차에는 평가를 사람 손에서 코드로 옮기는 일, 답변 캐시, 클라우드 배포 묶음, 그리고 공식 제출 결과(#30)의 오거부 원인 추적을 했다. 이 글에는 오늘 한 일과 함께, 새로 배운 점과 막혔던 곳을 정리해 둔다. 이전 글에서는 2~4일차의 인수인계와 첫 제출을 다뤘다.

오늘의 한 줄 정리

  • 평가는 자동 계산 + 회귀 비교로 해야 버전 간 비교가 가능하다.
  • 캐시는 키에 넣는 값이 곧 정확성이다.
  • 오거부처럼 보여도 원인은 검색 단계일 수 있다. 생성 단계만 보지 않는다.

  • eval/compare_runs.py: 제출 전 회귀 비교. 나빠진 문항과 좋아진 문항을 보여 준다. (#103)
  • Streamlit 시연 화면과 평가 결과 페이지를 만들었다. (#104, #110)

2. 지표 자동 계산과 회귀 비교

지금까지는 손으로 채점해서 버전끼리 비교하기가 어려웠다. 그래서 실행 로그와 정답표를 넣으면 지표가 자동으로 나오게 했다. 계산하는 지표는 Hit@5, Evidence, Answer, Abstention, False Answer, P95, 토큰이다.

  • 자동 계산이 믿을 만한지 확인하려고, 예전 로그로 다시 계산해서 손 채점과 같은지 검증했다.
  • 제출하기 전에는 compare_runs.py로 회귀 비교를 한다. 이전 실행과 비교해서 나빠진 문항과 좋아진 문항을 보여 준다.

3. 캐시 키에 넣어야 하는 값

답변 캐시의 키에는 질문만 넣으면 안 된다. 아래 값까지 함께 넣어야 한다.

키에 넣는 값 설명
질문 기본 값이다
제품 코드 모델만 다른 질문(T830와 T835)을 구분한다
설정 키에 함께 넣는다
동의어 파일 해시 키에 함께 넣는다
커밋 코드가 바뀐 뒤를 구분한다

이렇게 해야 모델만 다른 질문이나 코드 변경 후에 옛 답을 돌려주지 않는다. 그래서 캐시는 키에 넣는 값이 곧 정확성이라고 정리했다.

4. 오거부의 원인은 검색 순위

공식 #30(79.29점)에서 오거부가 4건 있었고, 원인을 추적했다. 원인은 "생성 판단"이 아니라 생성 모델이 받은 상위 5개 발췌에 답이 없는 것이었다. 즉 검색 순위 문제다.

이 실험에서는 형제 청크 확장도 시도했다.

5. 결과의 흔들림

같은 질문도 실행마다 1~2문항 흔들린다. 그러므로 한 번의 결과만 보고 개선 여부를 판단하면 안 된다. 회귀 비교와 자동 지표가 필요한 이유이기도 하다.

6. 막힌 점과 해결

문제 해결
손 채점이라 버전 비교가 어려움 지표를 자동 계산하고, 예전 로그로 다시 계산해서 손 채점과 같은지 검증
Supabase 팀 계정에는 스키마 생성 권한이 없음 코드에 박힌 rag 스키마를 설정으로 바꾸고, 이미 있으면 만들지 않게 함
DBeaver에서 "Unknown host" 오류 Host 칸에 "Session pooler"라는 글자가 들어가 있었다
